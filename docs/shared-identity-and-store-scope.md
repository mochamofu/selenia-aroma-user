# 2つのアプリで顧客を同一人物として扱う設計

作成日: 2026年9月4日
対象: `selenia-aroma-user`（お客様用・スマートフォン）と
`selenia-aroma-master`（サロン運営者用・PC/タブレット）

---

## 1. 前提：アプリは2つ、データは1つ

| | お客様用 | サロン運営者用 |
| --- | --- | --- |
| 端末 | iPhone / スマートフォン | iPad / PC（Webアプリ） |
| リポジトリ | `selenia-aroma-user` | `selenia-aroma-master` |
| 見るもの | 自分の記録だけ | 担当した顧客の記録 |

**画面は2つに分かれるが、データベースは1つ（Cloudflare D1）を共有する。**
これが「同じ番号の人を同じ人として扱う」ための土台になる。

アプリごとにデータベースを分けると、同じ人が2つの番号を持ってしまい、
どちらが本物か分からなくなる。分けない。

---

## 2. 顧客番号だけで、その人の情報を全部たどれるか

**たどれる。** 8桁の顧客番号は、DBの中で1人に1つだけ存在する。

```
01260051
││││└┴┴┴─ 店舗内の連番（0051 = 51人目）
││└┴───── 年度（26 = 2026年度）
└┴─────── 初回登録した店舗（01 = 銀座店）
```

- スキーマ上 `profiles.customer_number` は **unique**。同じ番号は2人に発行されない
- 8桁の数字であることを DB のCHECK制約で強制している（`0001_initial.sql`）
- 先頭2桁は「**初回登録した店舗**」を表すだけで、その人の所属を固定しない

### この番号からたどれるもの

| 知りたいこと | どこにあるか | たどり方 |
| --- | --- | --- |
| 氏名・カナ・生年月日 | `profiles` | 番号そのものが載っている行 |
| ヒアリング（悩み・健康・服薬） | `hearing_sheets` | `user_id` で紐づく |
| 脳波測定の画像 | `brainwave_images` | `user_id` で紐づく |
| **オイルの配合結果** | `aroma_records` + `aroma_ingredients` | `user_id` → 記録 → 材料 |
| 使ったベースブレンド | `aroma_records.base_blend_id` | ブレンド表へ |
| 内部配合比率（非公開） | `base_blend_private_recipes` | 事業者のみ閲覧可 |
| どの店舗に何回来たか | `visits` | `user_id` で紐づく |
| 誰がいつこの人の情報を見たか | `audit_logs` | `subject_user_id` で紐づく |

つまり、**番号 → 人 → その人のすべての記録**、が1本でつながる。

### 番号と内部IDの使い分け

- `customer_number`（`01260051`）… **人に見せる番号**。口頭・紙・画面で使う
- `user_id`（`user-sakura`）… **プログラム内部のID**。テーブル同士を繋ぐのに使う

顧客番号は運用上あとから採番ルールを変えたくなる可能性があるため、
テーブル同士の連結は `user_id` で行い、顧客番号は「人が使う鍵」に徹させている。
どちらから引いても同じ人にたどり着く。

### 2つのアプリでの見え方

同じ `user_id` を、お客様用アプリでは「本人だけが自分の記録を見る」、
運営者用アプリでは「担当者がその人の記録を見る」という形で使う。
**別々のアカウント体系を作らない**ので、突き合わせの作業が発生しない。

## 3. 店舗ごとの見え方

### 決めたこと

| 誰が | 顧客一覧に出るもの |
| --- | --- |
| 施術者（店舗スタッフ） | **自分の店舗に来店した人だけ** |
| 管理者（最高権限・小杉様） | **全店舗のすべての顧客** |
| お客様本人 | 自分の記録だけ（他の人は一切見えない） |
| 未ログイン | 何も見えない |

### 「その店舗の人」を所属ではなく来店で決める

ここが設計の要点。

所属（`profiles.store_id`）で決めると、**銀座で登録した人が大阪へ行ったとき、
大阪の一覧に出てこない**。担当者は「この人は初めてだ」と思って新しいカルテを作り、
同じ人が2つの番号を持つ事故が起きる。

そこで `visits`（来店記録）テーブルを作り、**その店舗に来店した事実**で判定する。

```sql
exists (select 1 from visits v
         where v.user_id = p.user_id
           and v.store_id = ?)
```

こうすると、銀座の常連が大阪に一度来た時点で、大阪の一覧にも
**同じ顧客番号のまま**載る。カルテは1本のまま繋がり続ける。

### 一覧は店舗ごと、検索は全店横断

| 操作 | 範囲 | 理由 |
| --- | --- | --- |
| 顧客一覧（`listStoreCustomers`） | 自店のみ（管理者は全店） | 普段使う画面に他店の人が混ざると探しにくい |
| 顧客検索（`searchCustomers`） | **常に全店横断** | 初来店の人・他店の常連を必ず呼び出せるようにする |

初めてその店舗に来た人は、まだ来店記録が無いので一覧には出ない。
そのときは氏名か顧客番号で検索する。検索は全店を見るので必ず見つかる。
**見つけて施術すれば `visits` に1行増え、次からは一覧にも出る。**

この2段構えにしないと、どちらかの事故が起きる。

- 一覧も全店にする → 問診中に他店の無関係な人の氏名が画面に並ぶ
- 検索も自店に絞る → 他店の常連が「新規のお客様」として二重登録される

## 4. 実装したもの

### スキーマ

`cloudflare/d1/0004_store_scope.sql`

| テーブル | 役割 |
| --- | --- |
| `store_staff` | 施術者がどの店舗に所属するか（複数店の兼務が可能） |
| `visits` | どの店舗で誰をいつ測定したか。一覧の絞り込みの根拠 |

### アクセス制御

`src/server/db/access.ts`

- `Viewer` の `operator` に `storeId` を追加。「どの店舗の画面として見ているか」
- `admin` は `storeId` を持たない。持たないことが「全店が見える」ことを表す
- `buildStoreCustomerScope()` … 上記の絞り込み条件を組み立てる唯一の場所

### 問い合わせ

`src/server/db/repositories.ts`

| 関数 | 内容 |
| --- | --- |
| `listStoreCustomers()` | 自店の顧客一覧（管理者は全店）。閲覧を監査ログに記録 |
| `listVisits()` | 1人の来店履歴を店舗名つきで新しい順に |
| `countCustomers()` | 一覧と**同じ絞り込み**で数える（数字と件数が食い違わないように） |
| `searchCustomers()` | 全店横断のまま（変更なし） |

### テスト

`src/server/db/repositories.test.ts` に「店舗ごとの見え方」を追加（11件）。
リポジトリ全体で **59件、すべて通過**。

確かめていること:

- 銀座の施術者に、大阪だけの顧客が出ない
- 大阪の施術者に、銀座だけの顧客が出ない
- **店舗をまたいだ常連は、両方の一覧に同じ顧客番号・同じ `user_id` で載る**
- 管理者には全店舗が見える（未来店の顧客も含む）
- 一覧に出ない他店の顧客も、**検索なら必ず引ける**
- 顧客数の集計も一覧と同じ絞り込みになっている
- お客様も未ログインも、店舗の顧客一覧を開けない

## 5. なぜD1でここまでやるのか

Cloudflare D1 には PostgreSQL の RLS（行レベルセキュリティ）が無い。
**アプリ側のチェックを1箇所でも書き忘れると、他人の健康情報が見える。**

そのため次の作りを守る。

1. 画面（`src/app/**`）から直接SQLを書かない。必ず `src/server/db/` を通す
2. 絞り込み条件の組み立ては `access.ts` の中だけ。呼び出し側に書かせない
3. 呼び出し側が `or` で条件を足しても絞り込みを外せないことをテストで確認する
4. 事業者専用テーブルは関数の入口で権限を判定する

`selectWithScope()` が絞り込みを必ず括弧で囲んで `and` で連結するため、
呼び出し側がどんな条件を足しても範囲は広がらない。テストで担保している。

## 6. 入口の見分け

2つのアプリの入口が似ていて、どちらを開いているのか分からないという問題があった。
それぞれのログイン画面に、誰向けかを言い切るバッジを入れた。

| アプリ | バッジ | 補足 |
| --- | --- | --- |
| お客様用 | **お客様用** | あなたのために調香したオイルの記録を、いつでも手元に。 |
| サロン運営者用 | **サロン運営者用** | PC・タブレット向け／お客様用アプリとは別です |
