# インフラ構成の方針（Cloudflare案）

作成日: 2026年8月17日
前提: 売上が立つ前の段階。固定費を限りなく小さく保つ。運営に常駐者はいない。
結論: **Cloudflareに寄せる。想定利用者1000人までは月額0円で収まる。**

## 判断の前提

月7,000円の固定費は、売上が立つ前の段階では通らない。
移行コスト（書き直しの手間）を一度払ってでも、ランニングコストを0に近づける方を選ぶ。

## 構成

| 役割 | 使うもの | 1000人時のコスト |
| --- | --- | --- |
| アプリの実行 | Cloudflare Workers（`@opennextjs/cloudflare`） | 無料枠内（10万リクエスト/日） |
| データベース | Cloudflare D1（SQLite） | 無料枠内（5GB、読取500万行/日） |
| 画像の保管 | Cloudflare R2 | 10GBまで無料。超過分は1GBあたり月$0.015 |
| 画像の配信 | R2 + Cloudflare CDN | **下り転送は常に無料** |
| 認証 | Better Auth（D1上で動かす） | 無料 |
| 独自ドメイン | Cloudflare Registrar または既存ドメイン | ドメイン代のみ |

### 無料枠に収まる根拠

- 脳波画像を1枚1MB、1人が年4回測定として、1000人で約4GB。R2の無料枠10GB内
- カルテ・顧客・制作記録のテキストは1000人で数十MB。D1の5GB枠に対して余裕
- 1000人が月に数回開く程度なら、Workersの10万リクエスト/日には遠く届かない

画像が10GBを超えても、超過分は1GBあたり月2円程度。40GB使っても月100円以内。

### Vercelの扱い

プレビュー確認用として無料のHobbyのままにしておく。Proにはしない。
本番はCloudflare側に置く。

## サポート体制について

Cloudflareの無料プランはコミュニティフォーラムとドキュメントのみで、日本語の個別サポートは付かない。
一方Xserver VPSは日本語のサポート窓口がある。ここはCloudflareの弱点になる。

ただし今回の用途では、サポートに頼る場面の大半が「サーバーが落ちた」「OSの更新で壊れた」といった
自前運用に伴う事故であり、Cloudflareのマネージド構成ではそれ自体が発生しない。
サポートの手厚さより、サポートを必要とする場面を作らない方を優先する。

## Xserver VPSを選ばない理由

すでに契約があり追加費用は小さいが、次を自分で見続ける必要がある。

- OSとNode.jsのバージョン更新、セキュリティパッチ
- Nginxの設定、SSL証明書の更新
- PostgreSQLの運用とバックアップ
- 障害時の復旧

常駐者がいない体制でこれを抱えると、事故が起きた日に誰も対応できない。
月額の差より、この運用負荷の方が重い。

## 書き直しが必要になる箇所

現状はSupabase前提で書かれているため、次の書き直しが必要になる。

| 対象 | 現状 | 変更後 |
| --- | --- | --- |
| DBスキーマ | `supabase/schema.sql`（PostgreSQL、UUID、配列型、RLS） | D1用のSQLite。配列型は別テーブルかJSON文字列に |
| 権限分離 | PostgreSQLのRLSポリシー | **アプリ層でのチェック**（下記の注意点） |
| 認証 | Supabase Auth | Better Auth（D1アダプタ） |
| 画像 | Supabase Storage | R2 |
| データ取得 | `src/services/*` がSupabaseクライアントを呼ぶ | 同じ関数の中身をD1/R2の呼び出しに差し替える |

`src/services/*` と `src/services/karteDraftStorage.ts` は画面から保存先を隠す層として
作ってあるため、画面側（`src/app/**`）の変更はほとんど発生しない見込み。

### 注意点: RLSが無くなる

これが今回の移行で一番気をつける点。

PostgreSQLのRLSは「SQLを書き間違えても他人のデータが返らない」保証をDB側で与えてくれる。
D1にはこの仕組みが無いため、**アプリ側のチェックを1箇所でも忘れると他人の情報が見える**。
扱っているのが健康情報・服薬情報なので、影響が大きい。

対策として、次の作りにする。

- DBへのアクセスは専用のモジュールに全て集約し、画面から直接クエリを書かせない
- 顧客本人向けの取得関数は、引数で受けたユーザーIDによる絞り込みを関数の中に固定で埋め込む
- 事業者向けの取得関数は、呼び出し元が管理者かどうかを関数の入口で判定する
- 上記が守られているかをテストで確認する

## 移行の順番

1. D1用のスキーマを作り、既存の固定データを投入して読み取りだけ動かす **（完了）**
2. アクセス制御を集約したモジュールを作り、権限のテストを書く **（完了）**
3. `src/services/*` の中身をD1呼び出しに差し替える（画面は変更しない）
4. Better Authでメール・パスワード認証を実装し、デモの自動入場を止める
5. 脳波画像をR2に保存する
6. Cloudflare Workersへデプロイし、独自ドメインを繋ぐ
7. 顧客番号（`customer_number`）を採番して保存する

各段階で動作を確認し、1つずつ進める。

### 完了している部分

| ファイル | 内容 |
| --- | --- |
| `cloudflare/d1/0001_initial.sql` | D1用のスキーマ |
| `cloudflare/d1/0002_seed.sql` | 既存の固定データの投入用SQL（自動生成） |

| `src/server/db/repositories.ts` | 画面から使うDB問い合わせの集約先 |
| `src/server/db/runner.ts` | D1と検証用SQLiteを同じ形で扱う層 |
| `cloudflare/wrangler.toml` | Workers設定のひな型（IDは要記入） |

### 次に必要なもの

CloudflareのダッシュボードでD1データベースとR2バケットを作成し、
`cloudflare/wrangler.toml` の `database_id` と `bucket_name` を記入する。
Database IDは秘密情報ではないため、そのままコミットしてよい。
