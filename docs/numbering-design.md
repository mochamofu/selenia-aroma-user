# 番号の付け方

作成日: 2026年9月4日

## 結論

**番号は2種類に分ける。1つにまとめない。**

| | 何を表すか | 桁数 | DBに入る値 | 表示 |
| --- | --- | --- | --- | --- |
| **顧客番号** | 人。一度発行したら一生変わらない | 7桁 | `2600123` | `CLT-2600123` |
| **施術番号** | 1回の測定+調香。二度と変わらない | 11桁 | `26090401001` | `LOT-260904-010-01` |

| | 何を表すか | 桁数 | 例 |
| --- | --- | --- | --- |
| 加盟店コード | 加入した順の通し番号 | 3桁 | `010` |

**「何回目の来店か」は番号に入れない。** 数えて出す。

---

## 1. なぜ分けるのか

ご提案いただいた `260904-010-001`（日付＋加盟店＋連番）は、**施術番号としては
ほぼ正解**です。ただしこれを顧客番号としても使うと、次の問題が起きます。

### 問題1: 同じ人が来店のたびに別番号になる

日付が入っているので、9月4日に来た田中さんと11月2日に来た田中さんが
別番号になります。「同じ番号の人は同じ人」という前提が崩れ、
2つのアプリで同一人物として扱えなくなります。

### 問題2: 「何回目」を焼き込むと、あとから全部ずれる

3回目として `...-003` を発行したあとで、

- 記録を取り忘れていた来店が見つかった → 本当は4回目だった
- 施術を中止して返金した → 本当は2回目のままだった
- 予約だけ入って来店しなかった記録が混ざっていた

このどれかが起きた瞬間、**それ以降の番号が全部意味を失います。**
そして番号は紙にもボトルにも残っているので、直せません。

回数は `visits` テーブルを数えれば常に正しい値が出ます。
番号に焼き込む理由がありません。

### 問題3: 加盟店を顧客番号に入れると、店が消えたあとも残る

これがご指摘の「うちの看板の店舗ではない」という点に直結します。

加盟店は独立したマッサージサロンやアロマ店です。ということは、

- 屋号が変わる（「新宿店」→「サロン◯◯」）
- オーナーが替わる、店を譲渡する
- 契約が終わる、閉店する

が普通に起きます。顧客番号に `010`（10番目の加盟店）と焼き込むと、
**その店が閉店したあとも、その顧客の番号は永久に `010` を名乗り続けます。**

「どの店で初めて受けたか」は手数料の配分に関わる大事な情報ですが、
だからこそ **列（`profiles.origin_store_id`）で持つべき**です。
列なら間違いが分かったときに直せます。番号は直せません。

## 2. それぞれの設計

### 加盟店コード — 3桁

```
010  ← 10番目に加入した加盟店
```

- **加入した順の通し番号。** 地名や系列を意味させない
- 一度発行したら変えない。**閉店しても欠番のまま再利用しない**
  （再利用すると、過去の施術番号が別の店を指してしまう）
- 999店まで。2桁（99店）では加盟店を増やす計画に対して足りない

**店名・オーナー・住所・連絡先はすべて `stores` テーブルの列**にしてあります。
いつでも変更できます。新しい加盟店の追加も1行の追加だけです。

```sql
create table stores (
  store_code text not null unique,  -- 変えない
  name text not null,               -- いつでも変えてよい
  legal_name text, owner_name text, contact_email text, phone text, address text,
  status text,                      -- active / paused / closed
  joined_at text, closed_at text
);
```

閉店しても**行は消しません**。`status = 'closed'` にするだけです。
消すと過去の施術番号がどこの店か分からなくなるためです。

### 顧客番号 — 7桁

```
26 00123
││ └┴┴┴┴─ 全加盟店で共通の通し番号（99,999人まで）
└┴─────── 年度の下2桁
```

- **人に一度だけ発行する。** どの加盟店へ行っても同じ番号を使う
- 通し番号は**全店共通**。店舗ごとに採番しないので、別の店で2つ目の番号が
  発行される事故が起きない
- 表示は `CLT-2600123`

**なぜ7桁か。** 入力の手間を最小にしつつ、必要な情報だけを残した結果です。

| 案 | 桁数 | 評価 |
| --- | --- | --- |
| 通し番号のみ | 5〜6桁 | 最短。ただし年度が読めず、何年の顧客か分からない |
| **年度+通し** | **7桁** | **採用。** 年度が読める。年間10万人まで対応 |
| 店舗+年度+通し | 9桁 | 店舗が読めるが、上記の問題3が起きる |
| 上記+チェックディジット | 10桁 | 打ち間違いを検出できるが、現場の入力負担が増す |

チェックディジットは採用していません。アプリ側で氏名検索ができ、
番号を打つのは補助的な操作にとどまるためです。
紙運用が中心になるようなら、あとから1桁足す判断はできます。

### 施術番号 — 11桁

```
260904 010 01
│      │   └┴─ その店舗のその日の連番（1日99件まで）
│      └┴┴─── 加盟店コード
└┴┴┴┴┴─────── 施術日 YYMMDD
```

- **1回の来店（測定＋調香）に発行する**
- **ボトルに貼るロット番号を兼ねる**
- 日付と店舗を焼き込んでよいのは、施術が**起きてしまったできごと**だから。
  あとから日付も場所も変わらない。ここが顧客番号との決定的な違い

番号1つで「いつ・どこで・その日の何件目か」が読め、
DBを引けば**誰の・どのレシピか**までたどれます。

### 接頭辞 — CLT と LOT

**数字だけを2種類並べると、設計した本人以外には見分けがつきません。**
施術を行うインストラクターが判別できないと運用になりません。
そのため、画面や紙に出すときは種類が読める接頭辞を付けます。

| 番号 | 接頭辞 | 由来 |
| --- | --- | --- |
| 顧客番号 | `CLT-` | CLienT（お客様） |
| 施術番号 | `LOT-` | ボトルのロット番号を兼ねるため |

`LOT-` はボトルに貼る番号として誰でも意味が分かり、
ハイフンの入り方（`CLT-2600123` と `LOT-260904-010-01`）も違うので、
数字を読まなくても一目で別物と分かります。

**DBには数字だけ（7桁 / 11桁）を入れ、接頭辞は表示のときに付けます。**
入力はどちらの形でも受け付けます。`CLT-2600123` と打っても `2600123` と
打っても、小文字でも全角でも、同じ番号として扱われます
（`normalizeNumber()` が吸収します）。

さらに桁数が違う（7桁 / 11桁）ため、**接頭辞を付け間違えても弾かれます。**
`CLT-260904-010-01` は顧客番号としては通りません。

## 3. 「何回目か」の扱い

番号に入れず、**数えて出します。**

```sql
-- この人の通算来店回数
select count(*) from visits where user_id = ?;

-- この加盟店での来店回数
select count(*) from visits where user_id = ? and store_id = ?;
```

こうすると、

- 記録漏れを後から足しても、回数は自動的に正しくなる
- 返金・中止した来店を除外しても、回数は自動的に正しくなる
- 「通算3回目、当店では初めて」のような表示も同じデータから出せる

番号に焼き込むと、このどれもができません。

## 4. ご要望の管理はこれで全部できます

> 一月のリスト化、顧客管理、注文管理をしやすくしたい

**番号に情報を詰め込んでも、集計は速くなりません。** むしろ文字列を
切り出して解釈する必要が出て遅く・危なくなります。集計は列で行うのが正解です。

| やりたいこと | 引き方 |
| --- | --- |
| 今月の施術を店舗別に | `visits` を `visited_at` の月と `store_id` で集計 |
| 加盟店ごとの売上・手数料 | `visits` × `store_id`。初回獲得分は `origin_store_id` |
| リピート率 | 1人あたりの `visits` の件数分布 |
| 特定の人の全履歴 | `user_id` で `visits` / `aroma_records` / `brainwave_images` |
| ボトルの番号から追跡 | `session_number` で `visits` を引き、そこから人とレシピへ |
| 何年度に増えた顧客か | `customer_number` の先頭2桁、または `profiles.created_at` |

`visited_at` と `store_id` に索引を張ってあるので、
月次リストも店舗別集計もそのまま速く出ます。

## 6. 移行について

**まだ本番のデータベースが存在しないため、いま変えるのが最も安いタイミングです。**
実データが入ったあとで番号体系を変えると、紙・ボトル・お客様の記憶に残った
番号との対応表を永久に持ち続けることになります。

運営者アプリ（`selenia-aroma-master`）の表示も `CLT-2600058` 形式へ揃えました
（PR #11、マージ済）。表示用の番号とURLに使う内部IDを同時に変えています。
片方だけ変えると、画面で見た番号を検索欄に打っても0件になるためです。

## 7. 残っている判断

| 論点 | 現状 | 判断が要るタイミング |
| --- | --- | --- |
| チェックディジットを足すか | 足していない | 紙運用が中心になったら |
| 1日100件を超える加盟店が出たら | 2桁（99件）で足りる想定 | 大型店が加盟したら |
| 年度の切り替わり | 暦年（1月始まり）で運用 | 会計年度に合わせるなら要変更 |
| 加盟店999を超えたら | 3桁 | そこまで増えたら嬉しい悲鳴 |
