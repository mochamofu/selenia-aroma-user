# サーバ側の認証

作成日: 2026年9月4日

## なぜ必要か

D1には PostgreSQL の RLS（行レベルセキュリティ）が無い。「他人のデータが返らない」
保証はアプリ層で作るしかなく、その判定の入口が「**いま誰が見ているか**」になる。

これを画面から渡された値で決めてはいけない。渡された値を信じると、
**他人のユーザーIDを送るだけで他人のカルテが読める**。扱っているのは
健康情報・服薬情報なので、影響が大きい。

そこで、`Viewer`（誰が見ているか）は**必ずサーバ側でCookieのセッションから作る**。
リクエストの本文やクエリからは決して作らない。

---

## 仕組み

### パスワード

```
pbkdf2$<繰り返し回数>$<salt>$<hash>
```

- **PBKDF2-SHA256**、10,000回（下の「繰り返し回数について」を必ず読むこと）
- 元のパスワードは保存しない
- salt は毎回ランダム。同じパスワードでも保存される値は毎回違う
- bcrypt / argon2 は Cloudflare Workers で動かないため使えない。PBKDF2 は
  標準のWebCryptoに入っており、追加の依存が要らない
- 繰り返し回数を保存値に含めてある。あとで回数を増やしても古い記録が
  そのまま照合でき、次回ログイン時に新しい回数で保存し直す

### 繰り返し回数について — 現時点の制約

OWASPの推奨は **210,000回**。いまは **10,000回**にしてある。
**この値は本来より低い。** そして**低くした根拠が確かめられていない。**

経緯を正確に残す。

1. 本番でログインが500になった
2. 「Workers の無料プランはCPU 10msが上限で、210,000回はそれを超えている」と
   判断し、10,000回へ下げた
3. その判断を**commitメッセージにもこの文書にも「実測した事実」として書いた**。
   実際には確認していない

**この説明は辻褄が合っていない。** 500が出ていた当時、パスワード違いのときは
401が返っていた。パスワード違いでも同じだけPBKDF2を計算しているので、
CPU上限が原因なら401も返せないはずである。原因は別のところにあった可能性が高い。

なお、現在の本番のログインは**正常に動いている**（正しいパスワード200 /
誤ったパスワード401 / 存在しないID401、いずれも3回ずつ確認）。

#### 確かめ方

`/api/health/pbkdf2?iterations=210000` を本番で開く。

| 結果 | 意味 | すること |
| --- | --- | --- |
| 200 `{"completed":true}` | 210,000回は本番で完走する。CPU上限は原因ではなかった | `PBKDF2_ITERATIONS` を **210,000へ戻す** |
| 500 / エラー | 210,000回は本番で通らない | 回数を段階的に下げて、通る上限を探す |

時間を測るのではなく「完走するか」を見ているのは、Workers では I/O が無い間
`Date.now()` が進まない仕様（タイミング攻撃対策）のため。計算だけを挟んでも
0ms としか出ず、時間は測れない。

#### いま何を諦めているか

| 攻撃の種類 | 影響 |
| --- | --- |
| オンラインからの総当たり | **変わらない。** 10回失敗で15分ロックしているため、回数の多少に関係なく試行そのものが止まる |
| **DBが漏れたあとの総当たり** | **弱くなる。** 手元で高速に試せるため、回数が少ないほど早く解かれる |

つまり「DBが漏れた場合の粘り」だけが下がっている。

引き上げは `PBKDF2_ITERATIONS` を変えるだけでよい。回数は保存値に含めてあるので、
古い記録もそのまま照合でき、次回ログイン時に新しい回数で保存し直される。

**実データ（実在のお客様の健康情報）を扱う前に、必ず210,000回へ戻すこと。**
仮に本当にCPU上限に当たるのであれば、Workers Paid（月$5 ≒ 750円）にすれば
上限を引き上げられる。実在の健康情報を扱う段階では妥当な費用。

### セッション

- ブラウザには32バイトの乱数（token）を渡す
- **DBには token の SHA-256 だけを保存する**
- こうしておくと、万一DBの中身が漏れても、そこからログイン状態を作れない
  （token をそのまま保存すると、DBが漏れた時点で全員になりすませる）
- 有効期間14日。使われ続けている間は延長する
- ログアウトでDB側の行も消す。Cookieを消すだけだと、控えられた token で戻れてしまう

### Cookie

| 属性 | 理由 |
| --- | --- |
| `HttpOnly` | 画面のJavaScriptから読めない。XSSがあってもセッションを盗めない |
| `SameSite=Lax` | 他サイトからの投稿でセッションが使われるのを防ぐ |
| `Secure` | httpsのときだけ送る（ローカル確認時は付けない） |

### 役割（role）の扱い

役割はセッションに焼き込まず、**毎回 `profiles` から読む**。
権限を落としたときに、発行済みのセッションが古い権限のまま生き残らないようにするため。

## 総当たりへの備え

| 対策 | 内容 |
| --- | --- |
| 応答を区別しない | 「IDが無い」と「パスワードが違う」で同じ文言・同じ状態コードを返す。区別すると、どのIDが登録済みかを外から調べられる |
| 応答時間を揃える | IDが無い場合もダミーのハッシュで同じだけ計算する。時間差から存在を推測されないようにする |
| 回数制限 | 10回続けて失敗したら15分受け付けない |

## ファイル

| ファイル | 役割 |
| --- | --- |
| `src/server/auth/password.ts` | パスワードの保存と照合 |
| `src/server/auth/session.ts` | セッションの発行・検証・破棄、Cookieの組み立て |
| `src/server/auth/login.ts` | ログインの判定、失敗回数の管理 |
| `src/server/auth/viewer.ts` | **リクエストから Viewer を決める唯一の入口** |
| `cloudflare/d1/0005_auth.sql` | `credentials` と `sessions` |
| `src/app/api/auth/*` | login / logout / me |

`credentials` を `profiles` と分けてあるのは、氏名などの表示用の情報と
パスワードのような秘密情報を同じ表に置かないため。取得のたびに秘密情報が
付いてこない。

---

## 守るべき決まり

1. APIルートは `getViewer(request)` だけを使う
2. **リクエストの本文やクエリからユーザーIDを受け取らない**
3. 受け取った `Viewer` を `src/server/db/` の関数へ渡す。画面から直接SQLを書かない

3が守られていれば、`access.ts` の絞り込みが必ず掛かる。

## 確認したこと

テストは**リポジトリ全体で115件**（認証で33件追加）。

**パスワード**

- 元のパスワードが保存値に含まれない
- 同じパスワードでも毎回違う値になる（saltが効いている）
- 正しいものは通り、1文字違い・空・末尾に空白は通らない
- 8文字未満は登録できない
- 壊れた保存値（平文、別方式、不正なbase64）は通らない
- 比較が長さ・中身で正しく判定される

**ログイン**

- 大文字や前後の空白があっても同じIDとして扱う
- **存在しないIDと、パスワード違いが、まったく同じ結果を返す**
- 10回失敗するとロックされ、正しいパスワードでも通らなくなる
- 成功すると失敗回数が0に戻る

**セッション**

- **token そのものではDBから引けない**（ハッシュでのみ引ける）
- でたらめな token、空、SQLらしき文字列では引けない
- 期限切れは引けない
- ログアウトすると使えなくなる
- 役割を落とすと、発行済みのセッションにも即座に反映される

**認証と権限のつながり**

- さくらのセッションからは、さくらの記録しか引けない
- 蓮のセッションからは、さくらの記録が引けない
- セッションが無ければ1件も引けない
- **他人の `user_id` を条件に足しても、自分のセッションでは他人の記録に届かない**

### Workers 上での通し確認

実際に `wrangler dev` で動かして確認した。

| 操作 | 結果 |
| --- | --- |
| 未ログインで `/api/auth/me` | `authenticated: false` |
| 誤ったパスワード | 401「IDまたはパスワードが違います」 |
| 存在しないID | **401、まったく同じ文言** |
| 正しいログイン | 200、Cookieが `HttpOnly` 付きで発行される |
| ログイン後の `/api/auth/me` | `role: customer` / 田中 さくら |
| 偽のCookie | `guest` |
| **他人のIDをクエリに混ぜる** | **無視され、自分の情報のみ返る** |
| ログアウト | 200、その後 `guest`、DBのセッションも0件に |

## 画面との接続

画面のログインはこの認証に差し替え済み。端末内(localStorage)にログイン状態を
持つ作りは廃止した。利用者が自分で書き換えられてしまうため。

デモ表示のときログイン画面を素通りしてダッシュボードへ入る動きも廃止した。
誰でも中身を見られる状態だったため。

制作記録もD1から読むようにした。取得時にユーザーIDを送らない作りで、
誰の記録かはサーバがセッションから決める。

| 画面 | 出どころ |
| --- | --- |
| ログイン | `/api/auth/login` |
| ダッシュボード・記録一覧・記録詳細 | `/api/records` `/api/records/[id]` |
| ベースブレンド・精油・気分 | `/api/catalog/*` |

### 通しで確認したこと（wrangler dev）

| 操作 | 結果 |
| --- | --- |
| 未ログインで `/dashboard` を直接開く | `/login` へ送られる |
| 未ログインで `/api/records` | 401 |
| 誤ったパスワード | 「IDまたはパスワードが違います」 |
| 正しいログイン | `/dashboard`、「こんにちは、田中 さくら」 |
| 記録一覧 | D1から3件（すべて本人のもの） |
| **他人の記録IDを直接指定** | **404** |
| 自分の記録IDを指定 | 取得できる（材料4件つき） |

## まだ残っていること

| 項目 | 内容 |
| --- | --- |
| パスワードの再設定 | メール送信の手段が決まってから |
| 施術者の店舗切り替え | 複数店を兼務する人向け。セッションの `store_id` を切り替える |
| 資格情報の管理画面 | いまは `scripts/seed-credentials.mjs` で投入する（デプロイ画面のチェックからも実行できる） |
| **繰り返し回数の引き上げ** | **実データを扱う前に必須。** 下げた根拠が未確認のまま。上の「繰り返し回数について」を参照 |
| 二要素認証 | 実データを扱う段階で検討 |

**現在登録されているのは検証用のアカウント1件のみ。**
実データを扱う前に必ず作り直すこと。
